---

## 2. 文件定位

本文件處理的是 HappyMeal 在前端呈現上的風格、互動與版面收斂原則。

本文件不是產品需求文件，也不是資訊架構文件。

分工如下：

1. 產品範圍、功能需求與驗收方向，以 `docs/PRD-v1.md` 為主。
2. 頁面目的、主流程與資訊層級，以 `docs/IA-User-Flows-v1.md` 為主。
3. 畫面樣式、互動細節、手機版排版與 UI 收斂方式，以本文件為主。

若 PRD、IA 與本文件之間沒有衝突，前端實作應同時滿足三者；若需求只涉及畫面收斂與互動細節，優先依本文件執行。

---

## 3. 目標與適用範圍

本文件主要適用於以下情境：

1. 首頁、分析流程、候選確認、結果頁、歷史頁、設定頁與個人資料頁的前端調整
2. 手機版 UI 簡化、版面重排與元件一致化
3. 表單、按鈕、卡片、提示訊息與底部導覽等互動元件的視覺收斂
4. 新功能上線前，確認是否延續既有 HappyMeal 風格

本文件不處理以下內容：

1. 資料模型、API 契約與後端服務邏輯
2. 視覺品牌重塑或全站重新設計
3. 超出 MVP 範圍的新產品模式

## 4. 核心體驗方向

### 4.1 手機優先

HappyMeal 以手機 Web 為優先，所有前端調整都應先從手機操作情境出發，再向上延伸到桌面。不要先做桌面版，再把內容硬縮到手機。

判斷標準：

1. 主要任務可單手完成
2. 主 CTA 清楚可見
3. 內容無需左右來回比對
4. 重要資訊不會被底部導覽或 safe area 遮住

### 4.2 輕盈、低壓迫、可快速理解

畫面目標是讓使用者快速理解下一步，而不是感受到系統複雜度。

因此畫面應避免：

1. 過多小字說明
2. 同一層級過多卡片競爭注意力
3. 像管理後台或工程工具的密集資訊排列
4. 把中介狀態、系統語言或內部用詞直接暴露在正式畫面

### 4.3 單頁單任務

每個畫面應聚焦單一主要任務。若某個區塊不是幫助使用者完成當前任務，優先弱化、後移或移除，而不是繼續往頁面中堆疊。

例如：

1. 設定頁應以更新資料與偏好為主，不應加入過多帳號摘要或系統資訊
2. 候選確認頁應優先呈現可修正的項目，而不是技術性中介資料
3. 結果頁應先呈現總結與可執行建議，再呈現次要明細

## 5. 文案與資訊密度準則

### 5.1 文案預設短句

文案優先短句與白話中文。能用標題、數字、按鈕文字與版面關係表達的內容，就不要再加第二層說明。

### 5.2 移除開發感與流程感語言

以下類型的文字不應長時間停留在正式畫面：

1. 目前流程
2. 系統狀態
3. Step 2 MVP
4. 類似 staging、debug、internal 這種內部語境強的字樣

除非是開發模式或除錯頁，正式畫面應改用使用者可理解的語言。

### 5.3 小字與輔助說明要節制

避免用小字堆疊補充說明來解決資訊設計問題。若資訊真的重要，應提升層級；若不重要，則應移除或後移。

### 5.4 成功提示與教學提示降噪

若操作結果已由畫面本身明確反映，就不要再額外顯示一次成功訊息。

例如：

1. 主題切換後若按鈕狀態已改變，就不需要再跳出「已切換成功」提示
2. 設定儲存後若需要提示，應使用短、明確、低干擾的方式

## 6. 版面與元件準則

### 6.1 優先沿用既有模式

新增 UI 元素前，先檢查能否沿用現有模式。若既有頁面已經建立某種按鈕、卡片、欄位或提示規則，後續頁面應優先複用，不要再發明新變體。

### 6.2 卡片與區塊節奏一致

同一頁中的卡片、欄位與操作區塊應維持一致的垂直節奏，避免某些區塊特別擠、某些區塊特別鬆，造成掃讀中斷。

### 6.3 單欄優先

設定頁、個人資料頁與分析修正頁在手機上應優先使用單欄堆疊與清楚分段，避免需要反覆上下或左右比對。

### 6.4 可點擊元件維持足夠高度

輸入元件、按鈕與選單應維持足夠高度與可觸控面積，不要為了視覺精簡而犧牲點擊穩定性。

### 6.5 原生控制項做最小一致化

下拉選單、數字欄位與其他原生控制項若造成視覺不一致，應以最小成本做一致化處理，例如：

1. 調整內距
2. 調整箭頭位置
3. 統一圓角與邊框節奏
4. 讓不同控制項高度一致

---

## 7. 表單與設定頁準則

### 7.1 直接優於花俏

表單、設定與修正流程應優先選擇直接、單欄、易懂的互動模式。若下拉選單比卡片式選擇更直接，就優先用下拉選單。

### 7.2 以完成任務為主

設定頁的主要目的是讓使用者快速更新資料與偏好，而不是閱讀系統背景資訊。

因此設定頁應避免：

1. 過多帳號摘要
2. 與當前任務無關的說明卡
3. 干擾表單節奏的提示區塊

### 7.3 主題切換保持簡潔

主題切換只改視覺語言，不改資訊架構、不改操作位置、不新增理解成本。主題切換元件本身應簡潔，不要附帶過多說明、提示條或裝飾性文案。

---

## 8. 流程狀態與分析頁準則

### 8.1 狀態切換要清楚，但文字要短

分析流程中的「上傳中」、「辨識中」、「候選確認」、「結果」等狀態切換，要讓使用者清楚知道現在在做什麼與下一步是什麼，但仍然維持短文案與清楚視覺層級。

### 8.2 候選確認頁聚焦修正

候選確認與結果頁面優先處理使用者最需要判斷或修正的資訊，不要把技術性中介資訊、除錯訊息或內部欄位直接暴露在主畫面。

### 8.3 輔助資訊保持後位

隱私政策與非醫療用途聲明在會員主要頁面中應保持可回看，但呈現方式要輕量，不可搶走主流程焦點。

---

## 9. 手機安全區與底部導覽準則

若畫面已有底部固定導覽、浮動 CTA 或 safe area 需求，內容底部必須預留足夠空間，確保：

1. 法律連結不被遮住
2. 最後一個表單欄位仍可完整操作
3. 次要操作不會被底部元件壓住

此規則應優先於純視覺對齊需求。寧可多留一點底部空間，也不要讓使用者碰到被遮擋的內容。

---

## 10. 實作與維護方式

目前前端大量頁面邏輯與樣式集中在 `frontend/src/App.tsx` 與 `frontend/src/styles.css`。

因此實作時應遵守以下原則：

1. 以小範圍、可驗證、低外溢影響的方式修改
2. 優先做局部收斂，不一次重寫大段結構
3. 每次改動後至少做一次前端 build 驗證
4. 手機版畫面若受共用 selector 影響，優先建立局部 class 或 modifier，而不是擴散修改全站規則

---

## 11. 使用建議

當需求涉及以下方向時，應主動參照本文件：

1. 畫面簡化或文案精簡
2. 設定頁、表單頁與分析流程頁的收斂
3. 主題切換、狀態提示與底部安全區調整
4. 任何「看起來太雜、太滿、太像開發頁」的 UI 修正

若需求未明確定義，前端調整應優先延續本文件所述的既有 HappyMeal 視覺語言與互動模式。
