## 2. 產品概述

HappyMeal 是一個以手機 Web 為主的營養與健身輔助服務。使用者可透過拍照或上傳食物圖片，取得 AI 食物辨識與營養估算，再結合自身身體數值與目標，獲得偏向增肌或減脂的基礎建議。產品預設視覺風格以年輕女性偏好為主，並支援男性向主題切換。

## 3. 產品目標

1. 降低使用者理解單次飲食營養內容的成本。
2. 讓使用者在少量輸入下獲得可執行的熱量與營養建議。
3. 提供熱門運動消耗熱量資訊，讓飲食與運動建議能放在同一個流程中理解。
4. 在第一版就控制隱私風險與健康聲明風險，避免產品定位偏向醫療服務。

## 4. 目標使用者

### 4.1 核心使用者

- 20 到 35 歲、習慣使用手機的女性使用者
- 對體態管理、飲食控制、增肌減脂有興趣
- 希望快速知道食物營養，而不是手動查大量資料

### 4.2 次要使用者

- 同樣有體態管理需求的男性使用者
- 需要更直接、指標導向資訊呈現的使用者

## 5. 市場與平台假設

1. 第一版目標市場以台灣、香港、日本等 LINE 普及市場為主。
2. 第一版平台以手機瀏覽器為主，桌機可用但不是設計優先。
3. 第一版會員登入以 LINE Login 為唯一登入方式。

## 6. 問題陳述

目前多數飲食紀錄工具有以下問題：

1. 輸入成本高，常需手動查找食物與營養資料。
2. 對一般使用者而言，熱量與三大營養素缺乏上下文，知道數字卻不知道該怎麼調整。
3. 飲食與運動建議常分散在不同工具中，難以形成單次行動決策。
4. 畫面資訊過密、專業術語多，容易造成使用者放棄。

## 7. 產品價值主張

1. 用拍照降低紀錄門檻。
2. 用 AI 幫助辨識與估算，而不是要求使用者先懂營養學。
3. 用簡化的增肌／減脂邏輯給出第一層建議。
4. 用舒適、低壓迫感的介面提高回訪意願。

## 8. MVP 範圍

### 8.1 納入範圍

1. LINE Login 註冊與登入
2. 個人身體資料建檔與編輯
3. 食物拍照與圖片上傳
4. AI 食物辨識與候選結果顯示
5. 使用者手動修正食物名稱與份量
6. 營養素估算：熱量、蛋白質、脂肪、碳水化合物
7. 增肌或減脂模式下的每日建議
8. 熱門運動熱量消耗資料查詢與推薦
9. 分析歷史摘要保存
10. 女性預設主題與男性主題切換
11. 隱私同意與非醫療用途聲明

### 8.2 不納入範圍

1. Google、Email、Apple 等其他登入方式
2. 社群、追蹤、排行榜、分享
3. 穿戴裝置串接
4. 專業醫療、疾病、孕期、慢性病營養建議
5. 週期化課表、餐單自動生成、教練級規劃
6. 原始照片長期保存
7. 後台 CMS 與複雜營運系統

## 9. 成功指標

### 9.2 品質指標

3. 分析回應時間
4. 登入成功率

## 10. 角色定義

### 10.1 訪客

- 可瀏覽首頁與產品介紹
- 可開始登入流程

### 10.2 會員使用者

- 可管理個人資料
- 可拍照分析食物
- 可查看分析結果與歷史紀錄
- 可切換主題偏好

## 11. 使用情境

1. 使用者剛吃完一餐，想快速知道這餐熱量與營養素。
2. 使用者正進行減脂，希望知道今天這餐是否偏高，並應如何調整。
3. 使用者想知道常見運動大概能消耗多少熱量，作為日常安排參考。

## 12. 功能需求

### FR-01 會員登入與帳號建立1

- 系統需支援 LINE Login OAuth 流程。
- 首次登入需自動建立帳號。
- 若 LINE 未提供 email，不可阻塞註冊或登入。

### FR-02 個人資料管理

- 使用者可建立與編輯年齡、身高、體重、活動量、目標類型、目標體重或方向、主題偏好。
- 系統需保存最後更新時間。

### FR-03 拍照與圖片上傳

- 系統需支援手機相機拍照與相簿上傳。
- 支援 JPG、PNG；其他格式可由前端轉換後送出。
- 系統需限制單檔大小與基本解析度。

### FR-04 食物辨識

- 系統需將圖片送往 AI 辨識流程。
- 系統需回傳 1 到 3 個候選食物結果與信心分數。
- 系統需提供標準化食物名稱，以利對應營養資料。

### FR-05 手動修正與份量確認

- 使用者可修改食物名稱。
- 使用者可刪除不正確的候選項目。
- 使用者可調整份量或輸入重量。

### FR-06 營養估算

- 系統需計算並顯示熱量、蛋白質、脂肪、碳水。
- 若為估算值，需明確標示估算性質。
- 系統需顯示每個食物明細與總和。

### FR-07 增肌／減脂建議

- 系統需依使用者身體資料與目標，產生每日建議熱量與三大營養素。
- 建議結果需包含簡短文字說明。
- 第一版不提供完整週計畫或逐餐菜單。

### FR-08 熱門運動熱量消耗

- 系統需提供至少 20 種常見運動資料。
- 系統需依使用者體重估算固定時長的熱量消耗。
- 系統可挑選 3 個推薦運動顯示在建議區塊。

### FR-09 分析歷史

- 系統需保存每次分析摘要。
- 歷史紀錄需包含分析日期、食物摘要、營養結果、建議快照。
- 不保存原始照片。

### FR-10 主題切換

- 系統需提供女性預設主題與男性主題切換。
- 切換結果需跨裝置保存於會員偏好。
- 第一版只改視覺語言，不改產品流程與資訊架構。

### FR-11 同意與聲明

- 使用者在首次使用身體數據與建議功能前，需同意隱私政策與非醫療用途聲明。
- 系統需保存同意版本與時間。

## 13. 非功能需求

### NFR-01 平台與裝置

- 以手機 Web 為優先。
- 支援主流行動瀏覽器。

### NFR-02 效能

- 主要頁面在登入後 2 秒內可互動。
- 單次分析流程目標 5 秒內回傳主要結果，p95 不超過 8 秒。

### NFR-03 可用性

- 每個畫面應有單一主要任務。
- 文字需精簡，避免長篇說明壓迫使用者。
- 主要操作需可單手完成。

### NFR-04 安全性

- 所有第三方 API 金鑰只能存放於後端。
- 所有流量需使用 HTTPS。
- 會員驗證需使用安全的 session 或 token 策略。

### NFR-05 隱私

- 原始照片僅作分析暫存，完成後刪除。
- 身體數據、目標、歷史分析視為敏感個人資料處理。

### NFR-06 合規與文案

- 不得使用診斷、治療、處方等醫療宣稱字眼。
- 所有建議內容需搭配非醫療用途聲明。

### NFR-07 可維護性

- 前後端分離。
- API 規格需文件化。
- 資料模型需保留後續擴充空間。

## 14. 驗收條件

1. 使用者可在手機完成登入、建檔、拍照分析與查看建議。
2. AI 辨識失準時，使用者可手動修正後完成流程。
3. 歷史紀錄可查看過去分析摘要與建議快照。
4. 系統不長期保存原始圖片。
5. 主題切換後重新登入仍保留偏好。
6. 所有建議相關頁面皆顯示非醫療用途提醒。

## 15. 風險與限制

1. AI 對複雜料理或混合餐的辨識準確率可能不足。
2. 營養估算本質上是估算，不可當作醫療或專業營養處方。
3. LINE Login 在非目標市場的普及率不足，因此暫不適合作全球版唯一登入方式。
4. 第一版若同時追求過多目標，會稀釋 MVP 驗證價值，因此先聚焦單次分析與個人化基礎建議。
