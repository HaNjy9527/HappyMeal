## 2. 驗測範圍

本輪以「已登入狀態」為前提，重點驗證 Priority 2 的核心主鏈，而非重新驗證 LINE Login。

本輪實測包含：

1. 真實圖片上傳與辨識結果分流
2. candidate review 的手機操作感受
3. re-estimate / AI 校正流程的可理解性
4. result / history 是否能反映分析結果

本輪不包含：

1. LINE Login regression 驗證
2. profile 不完整時 generic recommendation fallback 驗證
3. 正式營養資料來源正確性驗證

## 4. 驗測結論摘要

本輪結論可先濃縮成 5 點：

1. 真實圖片辨識主鏈已可用，AI 對實物外觀的判斷比預期好，至少已能把塑膠瓶飲料辨識成茶類 / 黑咖啡類候選，而不是完全失敗。
2. complete failure 路徑有效，故意拍衛生紙時，系統沒有硬湊成食物，而是正確回到「這次沒有穩定辨識出食物」的重拍提示，這應視為成功案例。
3. 原先缺少的「正在辨識中」回饋已補齊，現在上傳後會立即進入明確的 loading state，降低等待時的不確定感。
4. AI 校正 / 新建議原本直接堆在 confirm 頁面下方的問題，已完成最小互動收斂：現在改為次級入口、單欄版本切換與底部決策區，手機焦點已明顯改善。
5. 黑咖啡營養結果明顯失真，這不是小誤差，而是會破壞結果可信度的問題；它不屬於辨識分流本身，而屬於 nutrition source / estimation strategy 的缺口。

## 5. 逐點觀察

### 5.1 真實圖片辨識能力：正向結果

觀察：

1. 使用塑膠瓶飲料測試時，AI 至少辨識出 tea drink 或黑咖啡類型，顯示 provider 對「包裝飲品」不是完全失效。
2. 這代表 Priority 2 的「真實圖片 -> 候選項目 -> candidate review」主鏈已具備基本可用性。

判讀：

1. 這一點支持 Priority 2 目前的核心判斷：辨識主鏈已通。
2. 後續若要改善，重點不是先懷疑 provider 完全不可用，而是處理 unit normalization 與 nutrition mapping 的可信度。

### 5.2 AI 校正 / 新建議 UX：已完成最小收斂，完整精修留待後續

原始觀察：

1. 「AI 校正」輸入框與「AI 新建議」面板直接堆疊在 candidate review 下方。
2. 在手機畫面上，使用者很容易把它理解成同一頁裡又多出一個新表單，而不是一個可選的第二層工具。
3. 使用者輸入說明後，畫面同時保留原本內容與新建議，缺少清楚的焦點切換。

已完成的收斂：

1. 已補上明確 CTA，讓 AI 校正不再以常駐輸入框形式直接佔住主畫面。
2. 已把 AI 新建議改成單欄版本切換檢視，讓使用者在手機上可切回「目前內容」或查看「AI 新版」，而不是同時閱讀兩份內容。
3. 已把最終決策收斂成底部操作區，聚焦在「保留目前內容」與「改用 AI 新版」兩個主要動作；重新補充描述則退回次級入口。

後續建議方向：

1. 先有一個明確 CTA，例如「校正 AI 建議」或「補充描述給 AI」。
2. 點擊後以 modal 或 bottom sheet 開啟輸入介面，而不是直接把輸入框常駐在主頁底部。
3. 送出後關閉輸入介面，進入清楚的等待狀態。
4. 若後續要再進一步強化，可改成 modal 或 bottom sheet 形式承接輸入與決策。
5. 若後續要進一步貼近原生手機體驗，可再補 safe-area 與更強的底部 action bar 視覺語言。

判讀：

1. 這個問題雖然源自 Priority 2 的 re-estimate 功能，但目前已完成 P2 所需的最小互動收斂。
2. 使用者現在已能在手機上清楚理解入口、查看版本與最終決策，不再像同頁堆疊的開發驗證區。
3. 若要做到較完整的 modal / bottom sheet 或更原生化的手機體驗，較適合納入 Priority 4 的手機 UX 收斂。

### 5.3 黑咖啡 420 kcal：結果可信度風險

觀察：

1. 黑咖啡分析結果顯示 420 kcal，但實際瓶身標示約為 7 kcal。
2. 這個落差已遠超過「估算值可接受誤差」範圍。
3. 問題看起來不是辨識出錯而已，而是辨識後的 nutrition source / portion interpretation / fallback mapping 明顯失真。

判讀：

1. 這一點不應視為 Priority 2 分流失敗，而應視為 Priority 3 的核心缺口已被真實案例驗證。
2. 這會直接影響 result 與 history 的可信度，因此優先級應高。

### 5.4 非食物圖片：complete failure 成功案例

觀察：

1. 故意拍衛生紙後，系統沒有硬產生食物候選。
2. 前端回到 start analysis，並顯示「AI 這次沒有穩定辨識出食物，請重拍或換一張更清楚的圖片」。

判讀：

1. 這是 Priority 2 成功案例，代表「完全失敗 -> 重拍 / 換圖」的分流方向成立。
2. 這個結果應明確寫回 Priority 2，作為 complete failure 驗收證據，而不是只記錄成功辨識案例。

### 5.5 上傳後沒有辨識中回饋：已完成回補

原始觀察：

1. 提供圖片後，畫面缺少明顯的 in-progress state。
2. 即使後端正在呼叫 AI，使用者仍可能以為系統沒有工作。
3. 這種不確定感出現在主鏈最關鍵的一步，風險高於一般小 UI 細節。

已完成的收斂：

1. 上傳成功後已立即切到明確的辨識中狀態。
2. 已補上 loading 文案與階段提示，讓使用者知道系統仍在處理中。
3. loading 畫面已提供更接近手機產品頁的資訊層級，而不是只顯示一段最小工程文案。

原建議方向：

1. 上傳成功後立即切到明確的「正在辨識中」狀態。
2. 顯示 loading 文案，例如「正在辨識圖片，通常需要幾秒鐘」。
3. 若等待超過一定時間，可補充次級提示，例如「仍在處理中，請稍候」。
4. 若失敗，再轉回目前既有的 complete failure 或 error message。

判讀：

1. 這確實屬於 Priority 2 範圍，且現在已完成，因此不再是 P2 阻塞項。
2. 後續若再調整，應屬於視覺精修與文案優化，而不是主鏈補洞。

## 6. 問題歸屬建議

### 6.1 建議仍留在 Priority 2 的項目

1. 上傳後缺少明確辨識中狀態。
2. re-estimate 最小互動收斂：至少要讓入口、等待、建議套用三段更清楚，不要讓使用者在同頁迷路。
3. P2-1 手機驗測文件化與驗收結論回寫。

以上 3 項現已完成，可自 Priority 2 關閉條件中移除。

### 6.2 建議移交 Priority 3 的項目

1. 黑咖啡熱量與三大營養素明顯失真。
2. 包裝飲料的份量單位、克重換算與 nutrition source 對齊。

### 6.3 建議移交 Priority 4 的項目

1. AI 校正改成 modal / bottom sheet 的完整互動重構。
2. safe-area 強化與更原生化的底部操作區視覺。
3. candidate review 與 re-estimate 在手機上的整體頁面節奏重整。
4. loading state 視覺微調：將「照片辨識中」圖案或文字移到卡片右側。參考：`S__93282310_0.jpg`
5. re-estimate 文案與命名降噪：移除「目前版本與 AI...」說明段落，並將「AI 新版」改為「新的內容」。參考：`S__93282309_0.jpg`
6. start analysis 首屏精簡：移除 `Quick start` 區塊、將「改用本機圖片測試」改為「上傳圖片」，並修正手機板跑版。參考：`S__93249538.jpg`
7. candidate review 欄位壓縮：label 與 value 保持同一行，降低垂直空間消耗。參考：`S__93241351_0.jpg`
8. re-estimate 決策區減鈕與 CTA 層級重整，降低下一步判斷成本。參考：`S__93241350_0.jpg`
9. result / history 小卡資訊單行化，例如「總熱量 420 kcal」。參考：`S__93241348_0.jpg`

### 6.4 不需要另外開項的事項

1. 衛生紙被判定為非食物，應直接記為 Priority 2 驗收成功案例。
2. 塑膠瓶飲料可被辨識為茶類 / 黑咖啡類，應記為 provider 已具備基本實物辨識能力的正向證據。

---

## 7. 對 Priority 2 狀態的影響

本輪實測後，較合理的判讀是：

1. Priority 2 核心主鏈已通，包含 success / partial / complete failure 三條路徑的方向都成立。
2. 原先兩個直接影響手機理解性的收尾項目，亦已完成回補：辨識中狀態回饋、re-estimate 最小手機互動收斂。
3. 因此以 P2 範圍來看，主鏈與手機理解性需求都已達可關閉條件。
4. 營養可信度問題已被真實案例明確驗證，應正式回寫為 Priority 3 的高優先缺口。

---

## 8. 建議下一步

建議順序：

1. 先做一輪 3 到 5 分鐘的手機 smoke test，重看 loading state、AI 新建議切換與底部操作區是否順手。
2. 若 smoke test 無回歸，可正式將 Priority 2 標記為完成 / 關閉。
3. 將本輪新增的 UI/UX 微調項目轉入 Priority 4 backlog，不再作為 P2 關閉前阻塞項。
4. 將黑咖啡案例帶入 Priority 3，作為 nutrition source / fallback mapping 的真實失真樣本。

### 8.1 關閉前手機 Smoke Test

建議用 3 到 5 分鐘完成以下檢查：

1. 以上傳一張可辨識圖片測試 loading state，確認上傳後會立即看到辨識中畫面，而不是停在原頁無反應。
2. 以上傳一張 partial 情境圖片測試 candidate review，確認低信心提示、編輯名稱、改份量、改單位與刪除項目仍可正常操作。
3. 在 re-estimate 輸入一句校正描述，確認 AI 新建議回來後可在「目前內容 / AI 新版」間切換，且底部只剩兩個主決策按鈕。
4. 點「保留目前內容」與「改用 AI 新版」各做一次，確認兩條路徑都能回到可完成 confirm 的狀態。
5. 以上傳一張非食物圖片驗證 complete failure，確認仍會回到重拍 / 換圖提示，而不是誤進 confirm。
