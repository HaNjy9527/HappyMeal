## 1. 概覽

本流程涵蓋從使用者上傳餐點圖片，到 AI 分析完成並回傳候選食物清單的完整過程。流程結束時，`analysis` 記錄的狀態會從 `DRAFT` 更新為 `AWAITING_CONFIRMATION`（等待使用者確認）或退回 `DRAFT`（辨識失敗）。

**本流程不包含**營養計算與建議生成，那屬於使用者確認後的另一條鏈，請參閱：[營養解析流程-參考文件-v1.md](./營養解析流程-參考文件-v1.md)

**涉及的服務模組：**

| 模組 | 路徑 | 職責 |
|------|------|------|
| `analysis_upload.py` | `app/services/` | 入口：驗證、存檔、協調整體流程 |
| `analysis_recognition.py` | `app/services/` | 呼叫 Provider、判斷辨識狀態 |
| `recognition_openai.py` | `app/services/` | 圖片前處理、呼叫 OpenAI、解析回應 |
| `recognition_normalization.py` | `app/services/` | 清洗與正規化 Provider 回傳的候選 |
| `recognition_provider.py` | `app/services/` | 定義共用資料結構 `ProviderCandidate` |
| `ai_event_log.py` | `app/services/` | 寫入 `ai_event_log` 表（best-effort） |

## 3. 各層詳細說明

### 3.1 上傳入口層 — `analysis_upload.py`

**前置條件檢查：**

| 條件 | 失敗時 |
|------|--------|
| `analysis.status == DRAFT` | HTTP 409 Conflict |
| `content_type` 屬於 jpeg 或 png | HTTP 400 Bad Request |
| 檔案大小 ≤ `ANALYSIS_MAX_UPLOAD_BYTES`（5MB）| HTTP 400 Bad Request |

**暫存檔處理：**  
圖片寫入 `ANALYSIS_UPLOAD_DIR`（預設 `tmp/analysis-uploads`），以 `{analysis_id}.jpg` 命名。不論辨識成功或失敗，`finally` 區塊都會呼叫 `delete_analysis_uploads()` 清除暫存檔。

---

### 3.2 辨識協調層 — `analysis_recognition.py`

負責將 Provider 例外轉換成統一的 `AnalysisRecognitionResult`，讓上層不需要感知 Provider 細節。

**`AnalysisRecognitionResult` 欄位：**

| 欄位 | 說明 |
|------|------|
| `recognition_status` | `SUCCESS` / `PARTIAL` / `COMPLETE_FAILURE` |
| `candidates` | 正規化後的候選清單 |
| `manual_review_required` | 是否需要使用者特別注意 |
| `fallback_reason` | 失敗原因（`no_reliable_candidates` 或 Provider 錯誤碼） |
| `message` | 顯示給使用者的提示文字 |
| `provider_input_tokens` | OpenAI input token 數（供寫 event log） |
| `provider_output_tokens` | OpenAI output token 數（供寫 event log） |
| `provider_latency_ms` | API 呼叫延遲（ms） |
| `provider_outcome` | `"success"` 或 `"failure"` |

---

### 3.3 Provider 層 — `recognition_openai.py`

#### 圖片前處理（V2-05）

由 `preprocess_image(image_path, max_px)` 執行：

1. 用 Pillow 開檔
2. 非 RGB 模式（如 RGBA PNG）→ 合成白底轉為 RGB
3. 長邊 > `max_px`（預設 1024px）→ 等比例縮小（`Image.LANCZOS`）
4. 儲存為 JPEG，quality=85，optimize=True
5. 輸出 bytes 與 `"image/jpeg"` mime type

關閉前處理（`IMAGE_PREPROCESS_ENABLED=false`）時，直接讀取原始 bytes，mime type 依副檔名決定。

#### OpenAI Prompt（版本 v1）

```
RECOGNITION_PROMPT_VERSION = "v1"
```

目前規則摘要：

- 辨識最多 5 種食物或飲料
- ⚠️ `food_name`：「Prefer Taiwan everyday meal names」（未強制正體中文）
- `normalized_food_name`：必須是 snake_case 英文
- `confidence_score`：0 到 1
- `portion_default`：正數
- `portion_unit`：限 `bowl`、`plate`、`box`、`cup`、`pcs`、`fillet`
- 不確定時回傳較少項目，而非強行猜測

#### Provider 例外處理

| 例外 | reason | HTTP（上層） |
|------|--------|-------------|
| `RateLimitError` | `quota_exceeded` | 503 |
| `BadRequestError` | `invalid_image` | 503 |
| `APITimeoutError` | `provider_timeout` | 503 |
| `APIConnectionError` | `provider_unavailable` | 503 |

所有例外均攜帶 `latency_ms`，供上層寫入 `ai_event_log`。

#### 回傳結構 `ProviderCallResult`

```python
@dataclass(frozen=True)
class ProviderCallResult:
    candidates: list[ProviderCandidate]
    input_tokens: int
    output_tokens: int
    latency_ms: int
    outcome: str        # "success" | "failure"
    reason: str | None
```

#### Mock 路徑（無 API Key 時）

依上傳的檔名決定假資料：

| 檔名包含 | 回傳 preset |
|---------|------------|
| `salad` | Chicken Salad + Boiled Egg |
| `rice` | Grilled Chicken Rice + Stir-fried Vegetables |
| 其他 | Grilled Salmon + Brown Rice + Steamed Broccoli |

---

### 3.4 正規化層 — `recognition_normalization.py`

`normalize_provider_candidates()` 對 Provider 回傳的每筆候選執行：

| 處理 | 規則 |
|------|------|
| 過濾 | `food_name` 或 `normalized_food_name` 為空 → 丟棄 |
| 清洗 | 去除頭尾空白 |
| `portion_unit` | 空白 → 補 `"serving"` |
| `portion_default` | `≤ 0` → 補 `1.00` |

## 4. 辨識狀態說明

| 狀態 | 條件 | `manual_review_required` | `analysis.status` 更新 |
|------|------|--------------------------|------------------------|
| `SUCCESS` | 所有候選 `confidence_score ≥ 0.6` | `False` | `AWAITING_CONFIRMATION` |
| `PARTIAL` | 任一候選 `confidence_score < 0.6` | `True` | `AWAITING_CONFIRMATION` |
| `COMPLETE_FAILURE` | 候選清單為空，或 Provider 拋出例外 | `False` | `DRAFT`（可重拍） |

閾值 `0.6` 定義於 `analysis_recognition.py`：

```python
PARTIAL_CONFIDENCE_THRESHOLD = Decimal("0.6")
```

## 5. 事件追蹤（`ai_event_log`）

本流程在以下時機寫入 `ai_event_log` 表，採 best-effort（失敗只寫 warning log，不中斷主流程）：

| event | 時機 | 關鍵欄位 |
|-------|------|----------|
| `openai_recognition` | API 呼叫完成後（成功或失敗均寫） | `outcome`、`input_tokens`、`output_tokens`、`latency_ms`、`prompt_version` |
| `recognition_result` | Provider 成功時，辨識狀態判斷後 | `outcome`（`success`/`partial`/`complete_failure`）、`candidate_count`、`manual_review_required` |
| `analysis_upload` | 整體流程結束後 | `outcome`、`latency_ms`（含存檔與辨識的總時間） |

查詢範例：

```sql
-- 最近 10 次辨識的 token 用量
SELECT created_at, input_tokens, output_tokens, latency_ms
FROM ai_event_log
WHERE event = 'openai_recognition' AND outcome = 'success'
ORDER BY created_at DESC
LIMIT 10;
```

## 6. 已知問題與待改項目

### ⚠️ food_name 語言不穩定

**問題：** Prompt 目前使用 `"Prefer Taiwan everyday meal names when appropriate"`，未強制正體中文。AI 有時回傳英文名稱（如 `"Grilled Chicken"`），有時回傳中文（如 `"雞腿"`），不穩定。

**影響：** RAG 向量查詢（`food_nutrition_embeddings` 表）以中文為主，英文 `food_name` 做跨語言 embedding 搜尋準確率偏低。

**待改：** 將 Prompt 中這行改為強制正體中文，並升版至 `RECOGNITION_PROMPT_VERSION = "v2"`。

### ⚠️ Prompt 未要求估計重量（g）

**現況：** AI 只回傳 `portion_default`（份數）與 `portion_unit`（單位），克重由 `portion_resolution.py` 的 preset 換算。對沒有 preset 的食物，fallback 估算偏差較大。

**討論中：** 是否讓 AI 額外回傳建議克重，作為無 preset 時的備用值。

## 7. 相關環境變數

| 變數 | 預設值 | 說明 |
|------|--------|------|
| `AI_API_KEY` | `""` | OpenAI API Key；空字串時走 mock 路徑 |
