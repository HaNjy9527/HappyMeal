# HappyMeal 部署與用量預估 v1

## 1. 文件資訊

- 文件名稱：HappyMeal 部署與用量預估
- 版本：v1
- 日期：2026-03-19
- 狀態：Draft
- 用途：評估第一版部署於 AWS + Vercel 的可行性，並建立 10 到 100 位使用者規模的初步容量估算基線

## 2. 結論摘要

HappyMeal 第一版採用 AWS（後端）+ Vercel（前端）部署。

原因如下：

1. 前端為 React + Vite，build 產出純靜態檔，適合以 Vercel CDN 部署。
2. 後端為 FastAPI，以 Docker 容器化後部署於 AWS ECS Fargate。
3. 資料庫為 PostgreSQL，使用 AWS RDS 託管實例。
4. 第一版流量規模預估僅 10 到 100 位使用者，尚未需要複雜的多區域、多服務網格或高併發架構。

但要注意，第一版的主要成本與延遲風險，不在前端，而在以下兩點：

1. AI 圖像辨識 API 呼叫次數與單次延遲
2. 圖片上傳與暫存處理的頻率與大小

## 3. 估算前提 Assumptions

以下估算以保守 MVP 前提進行：

1. 註冊使用者總數介於 10 到 100 人。
2. 每日活躍使用者比例約 20% 到 30%。
3. 每位活躍使用者每日進行 2 到 5 次食物分析。
4. 每張上傳圖片平均約 1 MB 到 2 MB。
5. 圖片僅短暫暫存於後端分析流程，不做長期保存。
6. 食物分析流程第一版以同步 API 為主，尚未拆成背景工作佇列。
7. 熱門運動資料、營養對照資料、同意紀錄與歷史摘要儲存在 PostgreSQL。

## 4. 建議部署拆分

### 4.1 前端 Frontend

- 平台：Vercel
- 類型：靜態站點 CDN
- 內容：React + Vite 編譯產物
- 責任：頁面呈現、登入狀態顯示、圖片上傳入口、結果頁展示

### 4.2 後端 Backend API

- 平台：AWS ECS Fargate
- 類型：Docker 容器化 Python Web Service
- 技術：FastAPI
- 責任：LINE Login callback、圖片接收、AI API 呼叫、營養估算、歷史寫入、同意紀錄保存

### 4.3 資料庫 Database

- 平台：AWS RDS
- 類型：Managed PostgreSQL
- 內容：使用者資料、個人檔案、分析摘要、建議快照、運動資料、同意紀錄

### 4.4 圖片暫存

- 平台：AWS S3
- Lifecycle Policy：1 小時自動刪除
- 用途：分析流程中的圖片暫存，完成後由後端主動刪除，Lifecycle Policy 為雙重保險

### 4.5 後續可選元件 Optional Later

- Redis：若未來要做快取、限流或背景工作佇列，可再加入
- Queue Worker：若 AI 分析流程延遲偏高，可把辨識流程拆成背景工作

## 5. 第一版資源建議

### 5.1 前端

- 若採靜態部署，計算資源需求極低。
- 第一版重點應放在快取策略、壓縮資產與圖片大小控制，而不是擴大前端機器規格。

### 5.2 後端 API

建議起始規格：

1. 1 個 API 服務實例
2. 1 vCPU
3. 1 GB RAM

這樣的起始規格通常足以支撐 10 到 100 位註冊使用者的 MVP 階段，前提是：

1. AI 辨識主要由外部服務負責，而不是本機執行大型模型
2. 不做原始照片長期保存
3. 單次分析流程沒有額外的大量 CPU 影像處理

### 5.3 PostgreSQL

建議起始規格：

1. 小型託管 PostgreSQL 實例
2. 5 GB 到 10 GB 儲存空間作為起始值

以目前資料模型來看，10 到 100 位使用者在 MVP 階段的資料量不會大，真正需要關注的是：

1. 歷史分析保留多久
2. 是否記錄大量 JSON 快照
3. 是否額外保存審計紀錄與事件紀錄

## 6. 10 到 100 人規模用量預估

### 6.1 使用情境估算表

| 註冊使用者數 | 預估每日活躍人數 | 每日分析次數 | 預估尖峰同時分析數 | 每日圖片上傳量     |
| ------------ | ---------------- | ------------ | ------------------ | ------------------ |
| 10 人        | 2 到 4 人        | 4 到 20 次   | 小於 1             | 約 4 MB 到 40 MB   |
| 50 人        | 10 到 15 人      | 20 到 75 次  | 1 到 2             | 約 20 MB 到 150 MB |
| 100 人       | 20 到 30 人      | 40 到 150 次 | 1 到 3             | 約 40 MB 到 300 MB |

說明：

1. 圖片上傳量以每次分析 1 MB 到 2 MB 圖片估算。
2. 尖峰同時分析數為粗估值，假設使用者行為分散於三餐與晚間時段。
3. 真正的外部成本可能主要來自 AI API 計費，而不是 AWS 本身的運算費用。

### 6.2 對系統負載的意義

在這個規模下，系統負載通常不會先卡在資料庫，而會先卡在：

1. 外部 AI API 回應時間
2. 上傳圖片處理時間
3. 後端等待第三方服務時的 worker 佔用

因此第一版的關鍵不是先做複雜分散式架構，而是：

1. 控制圖片大小
2. 盡量縮短同步分析鏈路
3. 為失敗重試、timeout 與 fallback 設計基線

## 7. 如何預估用量與成本

建議用以下公式建立每月估算：

### 7.1 核心公式

- 每日分析次數 = 每日活躍使用者數 × 平均每日分析次數
- 每月分析次數 = 每日分析次數 × 30
- 每月圖片流量 = 每月分析次數 × 平均圖片大小

### 7.2 範例

若以 100 位註冊使用者估算：

1. 每日活躍使用者 25 人
2. 每人每日分析 3 次
3. 平均圖片大小 1.5 MB

則可得：

- 每日分析次數約 75 次
- 每月分析次數約 2,250 次
- 每月圖片流量約 3,375 MB，約 3.3 GB

這個數字尚未包含：

1. 前端靜態資源下載流量
2. AI API 自身按次或按量計費
3. 日誌、監控與錯誤追蹤額外流量

## 8. 什麼時候需要升級架構

若出現以下情況，建議從單一 API Service 升級為 API + Worker 模式：

1. 分析流程 p95 長期超過 `8` 秒
2. 單日分析次數穩定超過 `300` 次
3. 尖峰同時分析數超過 `5`
4. AI API timeout 或重試比例開始顯著拉高
5. 後端記憶體因圖片處理或 JSON 快照持續逼近上限

## 9. 建議下一步

1. 前端部署至 Vercel，後端以 Docker image 部署至 AWS ECS Fargate，資料庫使用 AWS RDS PostgreSQL。
2. 在後端加上分析流程的耗時記錄、錯誤率記錄與第三方 API timeout 記錄。
3. 先以 100 位註冊使用者、25 位 DAU、75 次每日分析作為第一版容量監控基準。
4. 若實際 AI 分析成本偏高，再評估圖片壓縮、快取、背景工作佇列與供應商切換。
